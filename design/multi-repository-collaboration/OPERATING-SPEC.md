# 仓库智能体：交互、决策与运行规则

状态：首期已实现（验收记录见 [技术设计 §11](./TECHNICAL-DESIGN.md#11-首期实现与验收记录)）。本文件细化 [产品方案](./README.md) 和 [技术设计](./TECHNICAL-DESIGN.md)，规定首期行为；默认值是产品建议，不代表当前引擎已具备对应能力。

## 1. 用户最短路径

1. 在“助手”中创建“订单研发”，绑定 order-api 和 admin-web，选择执行环境。SOUL、AGENTS.md 可从模板初始化，知识、记忆、Skill、MCP 均可按需配置，无需为了创建智能体把六项全部填满。
2. 点击“检查配置”，查看绑定仓库可读写性、适用规则、必需能力和实际隔离情况；通过后启用。检查不修改业务文件，也不自动安装或连接未配置的外部服务。
3. 会话输入框选择“订单研发”，发送“给订单详情增加优惠金额展示”。此时接收者、模式和目标范围都在输入框可见。
4. 智能体检查现有接口，在原会话给出简要分工并开始执行。用户可直接查看任务、调整要求或暂停，无需手动创建前后端会话。
5. 原会话持续呈现交付、联调问题和修正结果；最终打开整体验收卡片查看各仓库变更与运行证据。

首次选择仓库智能体默认“执行需求”；原有普通聊天会话保持原行为，不因升级自动转为代码执行。切换模式仅影响下一次发送，不追溯改变已经启动的需求。

## 2. 智能体配置和生命周期

### 2.1 编辑页

| 区域 | 必要内容 | 主要操作 |
| --- | --- | --- |
| 概览 | 名称、职责、状态、引擎/模型、默认主责项目 | 保存草稿、检查配置、启用、停用、复制、归档 |
| 绑定仓库 | 项目、仓库、角色、职责、读/写范围、是否默认负责 | 绑定、解绑、修改职责、查看专用配置 |
| 灵魂设定 / 工作规则 | SOUL.md、智能体 AGENTS.md 及版本 | 编辑、导入、比较版本、查看仓库适用规则 |
| 知识 / 记忆 | 独立条目、来源、范围、版本、有效状态 | 添加/订阅知识、查看/修订/删除记忆 |
| 技能 / MCP | 启停、版本、适用仓库、必需/可选、连接及工具状态 | 选择已有能力、禁用、检查实际生效 |
| 运行策略 | 默认执行模式、并发上限、修正预算、委派关系 | 调整策略、查看运行中的需求 |

“查看实际生效配置”必须先选择仓库和执行环境，展示每一项来自基础配置、仓库覆盖还是仓库原文件；不能把所有仓库的配置简单拼在一起预览。

保存草稿不改变已发布版本。发布新版本影响后续新需求；运行中需求继续使用快照，除非显式升级。回退也是发布一个新的版本，保持递增历史，不删除旧版本记录。

### 2.2 生命周期

```text
草稿 → 检查通过 → 启用 → 停用 → 重新检查并启用
草稿/停用 → 归档
```

身份生命周期与配置可用性分开：启用的智能体可能因凭据失效或仓库离线显示“配置待处理”。存在必需能力缺失时，阻塞相应新执行；可选能力不可用时移出本次生效清单，并明确显示降级原因，不强制整条需求停工。

停用后拒绝新派发和新尝试，已有执行请求在检查点停止；若正在提交交付，先完成该次事务再停止。归档前不能存在仍在执行的 attempt；历史需求继续显示原身份。重新启用先重新检查能力，不盲目恢复此前的所有需求；已暂停需求仍须按原控制状态处理。

已有需求可“更换负责人”：选择覆盖剩余任务的智能体，校验范围与能力，停止旧协调执行，再生成新的主责配置和计划版本。原负责人、执行者、消息和产物均保留历史。移交的是授权任务和检查点，不自动移交私有记忆、技能配置或凭据。

## 3. 输入框与需求关联

### 3.1 三种显式模式

| 模式 | 发送后行为 | 允许读代码/知识 | 允许业务修改 | 何时开始执行 |
| --- | --- | --- | --- | --- |
| 讨论 | 在当前会话回答，可引用资料 | 是，在当前读取范围内 | 否 | 不启动 |
| 先规划 | 创建待启动需求，生成计划和验收条件 | 是 | 否 | 用户点击该计划的“开始执行” |
| 执行需求 | 创建需求、自动判断和启动有效计划 | 是 | 是，在已授权范围内 | 计划校验通过即启动 |

模式比关键词优先：在讨论模式输入“实现某功能”也不启动修改，回答中可提供“作为需求执行”。执行模式只允许已约定范围内的动作，不能把“帮我实现”解释为自动部署生产环境。

### 3.2 关联规则

| 用户操作 | 目标需求 | 系统行为 |
| --- | --- | --- |
| 选择“新需求”并发送 | 新建 | 为该发送生成稳定 requestId，重复投递返回同一需求 |
| 点击卡片“继续此需求”后发送 | 指定 requirementId | 作为追加输入处理，携带当前 requirementRevision |
| 当前会话明确绑定一个活动需求 | 已绑定需求 | 输入框显示“继续：订单优惠展示”，允许切换新需求 |
| 多条需求且没有明确绑定 | 未定 | 暂存输入，请选择需求或新建；不执行有歧义的修改 |
| 继续已完成需求 | 原需求 | 创建重开记录、新验收轮次和必要任务，保留原完成证据 |
| 继续已取消需求 | 原需求 | 展示“重新打开”动作；仅发聊天消息不能自动复活取消项 |

一个输入可选择一个主责智能体。提及第二位智能体可作为建议执行者，但不能因文本含多个 @ 就向所有人复制整条需求。其他现有 @ 仓库/角色的批量派发入口保持原功能；智能体需求路径必须显式区分。

### 3.3 原会话展示

```text
订单研发 · 订单优惠展示                    [查看需求]
判断：后端尚无优惠字段，需要修改 2 个仓库。
计划：后端接口 → 管理前端 → 金额展示联调
当前：等待后端修正 FIX-17；前端进度已保存。
最近交付：orders-api@1 · 查看接口 / 测试 / 变更
[补充要求] [暂停需求] [查看协作消息]
```

进度采用持久事件投影，不要求 Agent 连续发送聊天文本。重复状态合并；正常步骤在卡片内更新，完成、失败、需要决策和用户配置的通知才触发提醒。用户离开原会话后可在需求列表继续处理。

## 4. 自主规划与反馈决策

### 4.1 仓库选择

| 观察到的证据 | 判定与行动 | 禁止的捷径 |
| --- | --- | --- |
| 现有接口字段和语义满足需求 | 仅创建必要前端实现及联调任务 | 因绑定了后端就强制改后端 |
| 需求要求的字段/能力确实缺失 | 创建后端任务，交付通过后放行前端 | 仅根据仓库名猜测接口存在 |
| 接口已有但文档陈旧 | 校验实际实现，安排契约/文档修正 | 只更新文档便宣称业务完成 |
| 需要的服务在未绑定仓库 | 展示仓库及需要的职责，进入范围决策 | 在磁盘上找到目录就自动写入 |
| 职责标签与源码实际不符 | 以源码/契约证据选任务，提出标签修订建议 | 自动重写项目永久职责配置 |

每次规划产物必须包含“选择了哪些仓库、为什么、哪些绑定仓库不需要改动”，以及可执行的验收条件。决策记录保存结论与证据引用，不要求保留模型私有推理过程，也不以自报置信度百分比代替证据。

### 4.2 联调责任

| 失败类型 | 必查证据 | 默认责任与后续 |
| --- | --- | --- |
| 契约承诺字段缺失或类型不符 | 契约版本、真实响应、失败断言、后端运行版本 | 后端修正，前端复验 |
| 前端解析/映射错误 | 响应符合契约，前端用例失败 | 前端自身修正，不派后端 |
| 连接失败、过期凭据、测试数据缺失 | 环境可达性、凭据引用状态、数据准备结果 | 环境准备任务；不消耗业务缺陷修正轮数 |
| 前端提出契约外字段 | 用户目标、领域知识及原验收条件 | 原需求已要求则补实现；否则范围决策 |
| 文档、接口和业务目标互相矛盾 | 各版本及对应来源 | 主责组织澄清，只阻塞受影响任务 |
| 后端认为是误报 | 可复现证据、拒绝理由 | 进入争议复核，不能由被指派方单方面解除前端阻塞 |

争议复核通过受控用例或明确人工决策结束：确认误报则记录 rejected/resolved 原因并重新评估消费者；仍是缺陷则继续 fixing。只有合并重复问题时，关闭副本并把消费者转移到主问题，不能丢掉等待关系。

### 4.3 最小验收门槛

智能体可以提出测试方案，执行器负责运行并绑定 commit、契约、环境、日志和结果。没有测试基础时，先创建最小契约或集成用例，再提交可验证交付。已有断言不可因失败而被静默删除、放宽或标记跳过；需要修改验收口径时记录需求修订及理由。

首期不强制必须有一个独立测试智能体，但必须使用运行证据；“同一个智能体写代码后声称测试通过”不构成证据。测试结果的权威性来源于受控执行记录与版本对应关系，不来源于 Agent 的自述。

## 5. 运行中追加要求与控制

### 5.1 追加输入的处理

| 类型 | 示例 | 处理 |
| --- | --- | --- |
| 补充既定实现细节 | “字段单位仍用分，页面按元展示” | 更新需求版本；受影响任务在检查点应用，其他任务继续 |
| 现有范围内追加缺失任务 | 原需求包括移动端但计划漏掉 | 修订计划，增加必要任务，无需重复授权既定范围 |
| 扩大业务范围 | 原来只做展示，现在要求发放优惠券 | 保存变更提案，标明新增范围和影响，待确认后修改计划 |
| 改变已有契约 | “把整数金额改成字符串” | 识别受影响消费者，显式采用新契约并重做对应验收 |
| 更换执行者或升级配置 | “交给后端专家继续” | 校验兼容性、保存检查点、释放旧租约，生成新绑定/配置快照 |

每次修订都保存“沿用 / 重做 / 新增 / 取消”任务列表。与修改无关且证据仍有效的任务可以继续；受影响的旧尝试结果可归档，但不得完成新版本需求。用户发送修改时看到的是“已接收补充 / 计划已更新 / 已应用”，三者不能混为成功提示。

### 5.2 控制与注意事项分开

需求运行控制为 `active / pausing / paused / cancelling / cancelled`。`needs_decision` 是带作用范围的待处理事项，不是默认暂停所有任务的总开关。

| 操作或情况 | 立即行为 | 已运行任务 | 后续恢复 |
| --- | --- | --- | --- |
| 暂停需求 | 停止新 claim、派发和恢复 | 保存检查点后停止，未停稳前显示“暂停中” | 恢复后重新检查版本、权限、环境 |
| 立即取消 | 停止新执行，发送停止请求 | 记录部分结果，确认退出后释放工作区；不得自动回滚用户代码 | 需明确重新打开，创建新 generation |
| 单任务需要决策 | 标记阻塞任务及下游 | 无关任务继续 | 决策解决后重新评估依赖 |
| 全局目标/授权不明确 | 阻塞需求范围内受影响操作 | 可继续不受影响的只读诊断 | 明确范围后继续 |
| 智能体停用 | 不接受该身份新执行 | 请求检查点停止 | 显式更换负责人或重新启用后继续 |

取消请求到达后，即使收到旧完成事件，也只保存证据；不能重新进入待验收。停止请求超时显示“停止待确认”，保留工作区锁和进程核对入口，不伪装成已取消且可重用工作区。

## 6. 并发、预算与资源回收

默认每个需求最多 2 个运行尝试，同时受 Wise 全局并发、运行环境并发和工作区写锁约束；不能突破用户已有更低上限。一个智能体可并发处理多条需求，但各需求的会话、上下文与检查点独立。

同一工作区同一时刻只允许一个写尝试；等待锁、依赖或修正不占模型执行槽位。主责等待期间释放槽位，否则“主责占着唯一槽位等待后端”会造成死锁。就绪任务按用户优先级与排队时间调度，避免同一条反复修正的需求无限抢占其他需求。

执行故障默认最多 3 次尝试（含第一次），业务修正默认最多 3 个后端修正轮次，计数分别持久化。消息投递退避不消耗模型执行次数。必需能力不兼容属于配置阻塞，不进行相同配置的无限启动重试。

可设置每需求总执行时长/用量预算；只有引擎提供可核实用量时展示精确用量，否则标为不可用或估算。预算耗尽停止新尝试，保留检查点并要求明确增加预算；禁止通过换会话清零。健康等待、人工等待不计入模型执行时长。

开发服务、临时端口、数据库夹具登记在需求环境清单中，注明所有者、消费任务和停止方式；不能停止用户自行运行的服务。多需求共享同一环境时使用引用计数，最后一个消费者释放后才按策略停止。完成或取消不自动删除未合并 worktree 和未审阅变更，清理入口展示保留内容与影响。

## 7. 完整示例与观察结果

假设订单研发绑定 order-api 和 admin-web；订单业务规范已经规定优惠金额为非负整数、单位分。

| 步骤 | 持久事实 | 用户可见结果 |
| --- | --- | --- |
| 输入框派发 | INTENT-1 → REQ-42，锁定智能体配置 V3 | 已接收，正在检查接口 |
| 自主规划 | PLAN-1：BE-1 → FE-1 → QA-1，记录源码与业务规范引用 | 需要修改两个仓库，后端先行 |
| 后端交付 | BE-1 提交 API-V1、commit B1、契约 C1 与接口测试 T1 | 后端接口可用，前端开始 |
| 前端联调 | FE-1 在特定订单数据下发现响应缺少 discountAmount | FIX-17 已交后端，前端已保存检查点 |
| 后端修正 | REPAIR-17-1 发布 API-V2、B2/C2/T2；校验通过 | 修正已交付，前端排队复验 |
| 前端恢复 | FE-1 新尝试引用 API-V2，重跑原失败用例并通过 | 前端复验通过，FIX-17 关闭 |
| 联合验证 | QA-1 固定 B2 + 前端 F1 + C2 + 环境 E2，生成验收清单 | 待验收，可查看变更与证据 |
| 验收与记忆 | 确认清单版本，需求完成；从证据生成范围受限经验 | 完成，相关经验可在智能体记忆中查看 |

API-V1 的接口就绪证据不保证覆盖所有业务数据，因此联调仍可能发现缺陷；修正后必须增加原缺陷的回归用例，不能只重复原来覆盖不足的测试。

若后端拒绝修正、用户中途暂停或配置权限变化，按前述规则分支处理；正常示例不能掩盖这些实际状态。人工点击“验收通过”时必须仍对应当前验收清单版本，避免用旧页面接受新变更。

## 8. 首期实现顺序与新增验收

先做 W0 运行能力验证，选定至少一种能够真实隔离配置的本地执行环境，再交付 M1 的完整纵向路径：创建智能体→输入框发送→持久规划→后端交付检查→前端接力。M1 必须包含 W4 的最小交付校验和会话回显，不能只完成数据库表。

M2 加入问题责任判断、争议复核、修正复验和运行中修订；M3 完成知识记忆生命周期、完整配置体验及所有异常验收。远程执行和语义检索仍属 M4，不阻碍首期本地多仓库使用。

| 编号 | 场景 | 可观察结果 |
| --- | --- | --- |
| AC-33 | 草稿发布、配置回退、停用及必需/可选能力失效 | 版本历史保留；草稿不影响运行；必需能力阻塞，可选能力显式降级；停用不接新执行 |
| AC-34 | 三种输入模式、多个 @、跨会话新建/续办 | 模式决定执行行为；一个主责；新建/续办关联明确，讨论与先规划不修改业务文件 |
| AC-35 | 运行中补充要求或改变契约 | 显示影响清单，无关任务继续；旧尝试不满足受影响的新需求版本 |
| AC-36 | 暂停/取消与完成回调竞争 | 未停稳显示中间态并保留写锁；取消后不复活；部分决策不阻塞无关任务 |
| AC-37 | 后端拒绝问题或把问题判为环境故障 | 有证据复核；不能单方面解锁消费者；环境故障不消耗业务修正轮次 |
| AC-38 | 全局并发为 1，主责等待；多个需求竞争，预算耗尽 | 等待释放槽位，无相互等待死锁；其他需求可执行；预算不因换会话重置 |
